A fast port scanner that gave wrong answers

14 October 2026

This month I built a port scanner in Python to learn how sockets and threads work. It is small and does one job: it tries to connect to each port on a machine and reports which ones answer. The code is on GitHub.

I only scanned my own computer and scanme.nmap.org, a server the Nmap project provides for light testing. Scanning machines you don't own, or don't have written permission to test, can be illegal.

How it works

The scanner makes a normal TCP connection to each port. If the connection succeeds, the port is open. If the machine refuses it, the port is closed. If nothing comes back before a timeout, I call the port filtered. A pool of threads runs many attempts at once, because waiting for silent ports one at a time is slow.

The result that surprised me

I scanned ports 1 to 100 on scanme.nmap.org with 1, 10 and 100 threads. My first runs used a timeout of 0.5 seconds.

Ports 1 to 100 on scanme.nmap.org, 0.5 second timeout
ThreadsTimeOpen ports found
131.52 s3 (22, 53, 80)
103.92 s1
1000.53 s0

The one-thread run found the three open ports. The faster runs found fewer, and the 100-thread run found none. It was the fastest and the most wrong.

My explanation

The server is far from me, so each reply takes a noticeable fraction of a second. A single thread with a 0.5 second limit just about copes. With many connections in flight, some replies arrived after the scanner had given up, and it marked those ports as filtered even though they were open. I haven't proven this with packet captures, but the next test supports it.

The fix

I raised the timeout to 2 seconds and ran the same three tests.

Same target, 2 second timeout
ThreadsTimeOpen ports found
132.70 s3 (22, 53, 80)
102.99 s3
1000.36 s3

Now every run found the same three ports, and 100 threads was about 90 times faster than one.

What I learned

A faster scan is only better if it gives the same answer. A timeout is a guess about how slow the network can be, and a guess that is too short fails quietly. The program printed a clean result and nothing in it hinted that anything was missing.

My scanner also puts every kind of failure under "filtered", including errors that have nothing to do with a silent port. Reporting those separately is the next improvement I want to make.

Limits

It only does full TCP connections, so it can't do stealth scans, UDP scans or operating system detection, and it shows up in the target's logs. I tested it against one remote server, so the exact timings will differ on other networks.
